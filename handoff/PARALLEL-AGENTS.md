# Working on Tessera alongside other agents

Read this whole page before you start. It gives you the development logistics for Project Tessera so you can work on your area without colliding with other agents working at the same time. Your specific assignment comes separately from the owner. When this page and your assignment disagree, ask the owner.

## 1. The project in one paragraph

Tessera is an AI-native learning management system prototype: courses (course → module → lesson → block), instructor authoring with AI drafts that a person must keep before students see them, a student experience with a hint-first tutor, and administrator governance. The owner (Jeff) is the sole developer and an instructional-design practitioner; he reviews visually and tests on the live site. Live site: https://tessera.edstratumlabs.ai/ (app at `/app/`, behind Cloudflare Access). Public docs: https://docs.tessera.edstratumlabs.ai/ (source in `mintlify/`). Repo: `theonlygeranium/project-tessera` (private).

## 4. Branches, worktrees, and merging

- Work on your own branch, in your own worktree, created from the latest `origin/main`:
  `git fetch origin && git worktree add ../tessera-<area> -b <area>/<short-task> origin/main`
  Then `npm install` in the worktree, or symlink `node_modules` from a checkout with the same `package.json`.
  Use a branch prefix for your area (for example `learner/…`, `admin/…`, `authoring/…`); don't use `agent/design-*` or `night*`.
- Never commit to or push `night4`; never force-push anything; never delete branches (the owner does that).
- **Rebase, don't let drift build.** When `night4` merges to `main`, rebase your branch onto the new `main` promptly and re-run the checks. Expect conflicts in the hotspots above; resolve them keeping both sides' additions.
- **Pushing to `main`** follows the deploy lanes in `CLAUDE.md` (D-013), with one extra rule while several agents are active: only a small change that touches no hotspot file may go straight to `main`, after rebasing and running `npm test` and `npm run typecheck`. Everything else goes to your branch, gets a preview, and the owner merges it (or asks you to).
- Commit messages end with a `Co-Authored-By:` line for the model that wrote the change (for example `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`).
- **Gate every commit and push on the checks' own exit status**, not on a `grep` of their output: `npx vitest run; st=$?` and then `[ $st -eq 0 ] && git commit …`. `grep` succeeds whenever it prints a failure line.
- Stage explicit paths when another process may be writing in the same worktree. Never `git add -A` in a worktree someone else is using.

## 6. Data, databases, and deploys

- **Previews share one database.** Every non-`main` branch preview uses D1 `tessera-preview`, including `night4`'s. A migration you apply there affects every preview. Schema changes must be additive (new tables, new nullable columns); never drop, rename, or rewrite data in the preview database. Apply with `npm run db:migrate:preview` **before** pushing code that needs the migration, and tell the owner in your report.
- **Production D1 (`tessera-prod`)** and production deploys are the owner's call: never migrate production or merge to `main` for a feature without his explicit OK. Before any production migration, take a D1 restore point (time-travel bookmark) and record it.
- **Previews lose their secrets on every push to an existing preview branch.** After each push, re-apply them: `tools/preview-secrets.sh <branch>` (it sets `WRITER_API_KEY` and `CF_ACCESS_API_TOKEN`). Without `WRITER_API_KEY` the preview silently uses the fixture AI.
- Branch preview URL: `https://<branch>-project-tessera.jeff-f69.workers.dev/` (lowercased; `/` becomes `-`). Cloudflare Workers Builds runs `npm run build` on every push; the preview is ready in about 30–60 seconds. Build logs: Cloudflare dashboard → Workers & Pages → project-tessera → Deployments.
- **Cloudflare credentials:** for any Cloudflare operation that needs an API token, read the owner's token at runtime from `~/.config/tessera/cloudflare-api-token`. Never print it, log it, commit it, or copy it into files. DNS, Access, and production changes still need the owner's explicit OK.
- **The docs site** deploys from `main`'s `mintlify/` folder. The `docs-sync` GitHub Action regenerates screenshots on every push to `main`, so don't commit screenshots from local runs.

- **All content in the repo is fictional** ("Meridian State", "Dr. Okafor", "Priya", "STAT 110"). Never commit real student data, real syllabi, or real people's details. The owner has shared real syllabi for testing; they live only in the gitignored `tests/fixtures/syllabus/private/`, and anything derived from them (evaluation reports under `reports/syllabus-*`) is gitignored too. - **Nothing under `docs/` may link into the private repo or contain confidential material**; branch previews are public too (D-012).
- **Public docs (`mintlify/`)** never mention internal tooling, AI coding agents (Claude, Codex, Grok), evaluation harnesses, answer keys, real syllabi, model-vendor internals, or other EdStratum products, and never link into the private repo. No decision codes in public text.

## 8. Hard rules you'll be checked against

From `CLAUDE.md` and the owner's standing preferences; reviews reject work that breaks them:

- **No colored edge stripes on anything** (D-017): no accent `border-left`/`border-inline-start`, no `inset Npx 0` box-shadow bars, on any element for any purpose (current items, callouts, cards, AI). Show state with fills, weight, text, or Tessera's markers. `npm test` includes a stripe guard.
- **AI content only through the Marginalia markup** (`AiContent` in the app; `.ai` / `.ai-who` / `.ai-src` / `data-state` on the site). Every AI element names what it is and its source. No sparkle icons or gradients for AI (D-006, D-018).
- **AI drafts never auto-publish** (D-003): a person keeps them; agentic actions are previewable change sets.
- **The tutor gives hints first** and follows the tutor mode; the answer key is never a source (D-005). **No "learning styles"** (D-004).
- **Tokens only** for color (`design/tokens.json`; app code reads CSS custom properties; never hard-code colors).
- **Accessibility:** real `<button>`, `<a href>`, `<input>` + `<label>`; icon-only buttons need `aria-label`; text contrast ≥ 4.5:1; 24 px minimum targets (44 px for learner touch targets); visible focus; focus returns to the control that opened a panel or dialog; content reflows at 320 px.
- **Model output is untrusted input.** Validators for AI output repair what is safe and reject only bad shapes; test them against messy, model-shaped input, not only the fixture.
- **Code that deletes or overwrites content** makes the condition part of the write (compare-and-set in both repositories), never check-then-write; get an Astra review before merging it.

- Install: `npm install` (Node 18+). Build the site: `uv run --no-project --python 3.12 --with 'markdown>=3.5' python tools/build_docs.py` (the Mac's default Python is 3.9).
- Everyday: `npm run typecheck`, `npm test` (vitest, includes the stripe guard and repo contract), `npm run build` (use `CACHE_DIR=/private/tmp/tessera-storybook-cache npm run build` if Storybook can't write its cache through a symlinked `node_modules`), `npm run a11y` (must print N/N pass; add every new page, state, and story to `tools/a11y_audit.mjs`), `npm run e2e` (Playwright journeys on the mock; `ONLY="Journey 21"` runs one).
- Local app: `npm run dev` (http://localhost:5173/app/); demo mode on the mock: `?data=mock&as=<user>` (`u-admin`, `u-okafor`, `u-priya`, `u-marcus`). Full Worker locally: `npm run dev:api` (restart it after changing `worker/` or `shared/`).
- Codex CLI: `/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex`; Grok CLI: `~/.grok/bin/grok`. Run them with the Claude Code Bash sandbox off and their own sandbox on, always with explicit model and sandbox flags (`codex exec -p tessera … --ephemeral -C <worktree>`; `grok … --sandbox workspace --cwd <worktree>`). The owner's global Codex default is `danger-full-access` and must never apply. ## 10. Definition of done, and how to report

Full lane (`CLAUDE.md`): source edited → build → `npm run a11y` with zero violations → `npm test` and `npm run typecheck` green → e2e for the affected journeys → walk the flow locally with screenshots → push your branch → re-apply preview secrets → check the preview in a browser → report. The owner merges.

Report to the owner with: what shipped (by file area), what the checks showed (numbers, not adjectives), anything you claimed (migration number, journey numbers, proposed decision), anything that needs him (visual review, a decision, a production step), the preview URL, and a **Next steps** block: a one-line status, then 2–4 numbered options with your recommendation first, each saying whether you'll do it or it needs his decision. Be direct; lead with the result; no praise or filler.
